## 結論

開始時点では、購入画面は存在したが、会員登録・本人情報編集・管理画面と検索条件の一部が未接続だった。
今回、既存の業務 API に対応する画面と権限制御を追加した。
API 単位の対応範囲は [対応表](API_COVERAGE.md) を参照。

## 連動のために修正したバックエンド

| 問題 | 修正内容 |
| --- | --- |
| パスワード未入力で会員情報を保存すると既存ハッシュを消す可能性 | `MemberMapper` で既存ハッシュを保持。新しいパスワードがある場合だけ更新 |
| 会員情報・商品書き込みの権限制御が不足 | 公開登録、本人の参照・更新、管理者専用操作を `ResourceAccessInterceptor` で区別 |
| ログイン失敗・管理者 API の認証失敗の HTTP ステータスが不一致 | 未認証・無効トークンを401、権限不足を403に整理 |
| 入力値や重複情報が一部未検証 | 年齢、会員編集、商品編集、在庫・公開状態・権限を検証。重複メールや関連データ制約を扱う |
| カートの販売状態・数量・合算数量が未検証 | 非公開商品、1未満の数量、在庫を超える数量を拒否 |
| 発送済み・完了済み注文も支払い処理に進める | 本人の未払い注文だけを決済対象に限定 |
| 管理者のキャンセルが在庫復元と連動しない | 許可された注文状況への遷移を検証し、キャンセル時に在庫を戻す |
| 決済・管理変更・自動キャンセルの競合 | 同じ注文行を `SELECT ... FOR UPDATE` で取得し、最新状態を再確認 |

データベースのテーブル定義変更はない。バックエンドの変更を反映するため、既存の Java プロセスは再起動が必要。
以前許可されていた一般会員による他人の情報操作・商品書き込みは、変更後は403となる。
この対応をセキュリティ監査や負荷・同時実行試験の完了とは扱わない。

## 中断後の追加修正

- 管理画面の新規会員フォームで、送信状態の変化によって入力内容が初期化されないよう修正。新しく開くときにはフォームを初期化する。
- 検索条件・表示件数の変更では、明示的に1ページ目を再取得する。
- 管理ダイアログの保存中は、背景クリックや Escape キーによる閉鎖を防ぐ。
- 管理者 API の無効トークン・削除済み会員を401として扱い、不正な権限値を400で拒否する。
- テスト用の Vite キャッシュを OS の一時フォルダーに分離し、終了後にそのフォルダーだけを削除する。

## 検証

2026年9月23日の実行結果：フロントエンド12件、バックエンド17件がすべて成功。`npm run build` と `git diff --check` も成功した。

- フロントエンド：`npm test`。Vue の初期描画、コンポーネント処理、API パラメーター、JWT、権限ガード、古い応答の無視、二重送信、決済後の明細保持などを検証。
- バックエンド：`mvn test`。実際の `WebConfig` を用いた MockMvc の権限検証、H2 と実際の Mapper によるパスワード保持、カート検証、注文状況・在庫復元を検証。
- フロントエンドの本番向けビルド：`npm run build`。
- テストは通信・サービスをモック化し、またはメモリー上の H2 を使用する。実際の利用者データベースへの注文作成・決済は行っていない。

ブラウザーでの画面操作、実際の MySQL・稼働中サーバーとの一連の購入操作、AWS への反映は未実施。
自動テストとビルドの成功だけで、これらの完了を主張しない。
ビルド時には主要 JavaScript チャンクの容量警告が残るため、配信容量の最適化は今後の課題。
注文の二重送信対策は画面内のもの。複数タブや通信断後の再送まで保証するには、バックエンドの冪等性設計が別途必要。

## ローカル確認手順

リポジトリ直下から、`package.json` があるフロントエンドフォルダーに移動する。

```powershell
cd ec-mall-frontend
npm.cmd test
npm.cmd run build
npm.cmd run dev
```

バックエンドはリポジトリ直下の `pom.xml` を対象に、IDE の Maven 操作または `mvn test` でテストし、
Java アプリケーションを再起動する。開発サーバーは `/api` を `http://localhost:8888` に転送する既存設定を維持している。
本番配信では、別途 SPA の履歴ルートと `/api` の転送設定が必要。デプロイ設定は今回変更していない。

1. 新規登録 → ログイン → 会員情報編集 → ログアウト → 同じパスワードで再ログイン。
2. 商品検索・ページ切替 → 数量を選んで追加 → カート数量変更・削除。
3. 配送先入力 → 注文作成 → 注文詳細 → テスト決済 → 明細と状況の確認。
4. 一般会員で管理画面の URL を直接入力し、拒否されることを確認。
5. 既存の管理者でログインし、商品・会員・注文の管理操作を検証用データで確認。
6. トークン期限切れ、サーバー停止、不明な URL で、適切な案内が表示されることを確認。

この一覧は実環境で行う受入確認の手順であり、実施済み記録ではない。
